# Silkscreen port of CrossPoint Reader

This branch (`silkscreen`) ports CrossPoint Reader to **Silkscreen**, an open-hardware ESP32-S3 e-paper reader base board and the successor of de-link. The hardware is described in `de-link_pcb/docs/HARDWARE.md` ([iandchasse/silkscreen-pcb](https://github.com/iandchasse/silkscreen-pcb)). The firmware-facing facts taken from it, with verification notes, are in [REQUIREMENTS.md](REQUIREMENTS.md). The sleep-current budget, the pin states in sleep and the battery-drain rules, with where each is implemented, are in [POWER.md](POWER.md). How the firmware handles the board's variants is in [MODULARITY.md](MODULARITY.md): the panel family is a build env, parts it can read are probed at boot, the front light is detected when the user switches it on, and the rest needs nothing.

- **Base:** CrossPoint `develop` at `d1509d07`, with freeink-sdk at its pinned `87c4493`. The SDK work is on the submodule's `silkscreen` branch.
  - Upstream `develop` is merged in up to its tip on 2026-10-01, `664528b2`. The SDK `silkscreen` branch merges freeink-sdk `2339226`, the commit that tip pins (merge `7384790`), and the parent's pointer is that merge. What the merges changed for Silkscreen, and how to take the next one, is under [Upstream merges](#upstream-merges).
- **Earlier attempt:** the first port (Sep 20-21, 2026) is archived in `EPD_Hub_ESP32/silkscreen-firmware-archive/` as git bundles plus `.patch` files. It is a reference only. Its pin map was right, but several behaviours contradict the hardware spec. They are listed under [What this port does differently](#what-this-port-does-differently).

## Architecture: Silkscreen is data

freeink-sdk describes each board as a `BoardProfile` in `libs/hardware/BoardConfig/include/BoardConfig.h`, and its rule is that feature code never keys off a device name. This port follows that rule.

- `FREEINK_DEVICE_SILKSCREEN`, `Board::Silkscreen` and the `SILKSCREEN` profile live only in `BoardConfig.h`.
- Every Silkscreen need that the SDK could not already express becomes a **new, defaulted field** that generic code reads. Existing profiles compile unchanged, and the defaults reproduce their behaviour.
- The mechanisms behind the ladder, charge-ladder, power-policy, I2C-recovery, display-probe, front-light-probe and identity-check fields are compiled in only with `FREEINK_CAP_ADC_LADDERS`, `FREEINK_CAP_CHARGE_LADDER`, `FREEINK_CAP_POWER_POLICY`, `FREEINK_CAP_I2C_RECOVERY`, `FREEINK_CAP_DISPLAY_PROBE_POLICY`, `FREEINK_CAP_FRONTLIGHT_PROBE` and `FREEINK_CAP_PROBE_IDENTITY` (on for Silkscreen, the front-light probe only with the light compiled in; the accessors `BoardConfig::hasAdcLadders()`, `hasChargeStatusLadder()`, `powerPolicy()`, `freeink::i2c::busRecoveryEnabled()`, `displayProbePolicy()`, `displayBusyPullUp()`, `touchIdentityCheck()`, `rtcIdentityCheck()` and `FrontlightManager::load()` / `stringMissing()` / `restoreAllowed()` fold to off without them), so the ESP32-C3 build and the other S3 boards do not carry them.
- **Cross-board changes (intentional fixes).** These apply to every board, with no profile field:
  - the light is begun only after the wake decision on every frontlit board, so a ghost wake or a USB-cold-boot re-sleep no longer flashes Restore Light on Wake;
  - `EpdBus::begin()` presets CS HIGH before SPI starts and RESET HIGH before its output is enabled;
  - `holdRailOff()` presets the level before enabling the output;
  - one ADC lock around every SDK ADC read (`SharedAdc.h`). Arduino's oneshot read only try-locks the unit and returns 0 to the loser, so on X4, X3 and de-link a render-task battery read could turn a concurrent key-ladder read into 0 (a phantom RIGHT/DOWN) or a battery sample into 0 mV;
  - touch drivers on the sensor-bus pins start the bus at `SensorsConfig::i2cHz` (`busHz()`), the clock every existing board already used;
  - `SDCardManager::shutdown()` and `detachFilesystemForRawAccess()` write SdFat's cached directory/data and FAT sectors back before dropping the volume (`FsVolume::end()` writes nothing), so a sector left dirty is not lost when the card's power is gated or a USB host takes the card.
- No `isSilkscreen()` in SDK feature code. The app uses board identity only for policy (OTA board tag, the keep-awake list).
- Which variations are a build choice, which the SDK probes (patching `BoardConfig::ACTIVE` before a driver reads it), which wait for the user and which are invisible is set out in [MODULARITY.md](MODULARITY.md#how-it-maps-onto-freeink-sdk).

| New generic mechanism | Why Silkscreen needs it (HARDWARE.md) |
|---|---|
| `parkedPins`: per-pin boot and sleep levels | EPD `CS` has no pull-up and must be HIGH before any SCLK edge (§6.1). `ADIM`/`COLOR_SEL` must be LOW at boot and in sleep (§7). `TP_RST` is held HIGH, never LOW, because the controller VDD is unswitched (§8). |
| `InputPins::powerExternalPull` | `IO18` already has `R76` 100 kΩ. An extra internal pull-down drags a press to ~2.5 V, marginal against VIH (§9.2). |
| `DisplayPins::busyPullDown` | `BUSY` has no external pull; a missing panel must not float. |
| `DisplayPins::busyPullUp` | The same for a UC8279's active-low `BUSY_N`, whose wait has no timeout: a missing panel must read idle, not hang the loop awake. |
| `BoardProfile::displayProbe` (`DisplayProbeConfig`: `forced`, `ultraChipController`, `cacheAcrossDeepSleep`, `x4ClassPanel`), `freeink::displayControllerSource()` | The panel is a GDEQ0426T82 (SSD1677) or the custom UC8279D panel, on the same pins (§6). The SDK display probe (`XteinkDetect`) tells them apart by a half-duplex read on SDI (IO12 via R29); any UltraChip answer is the UC8279D, the verdict must never go stale in NVS, and a probe that misbehaves needs a build override. |
| SDMMC: `maxFreqKhz`, `internalPullups`, `parkLowWhenOff`, power-off/settle times | The external 10 kΩ pull-ups go to the *gated* `SD_VDD`. Internal pull-ups to 3V3 back-feed a gated card. A real power cycle needs the bus driven LOW for at least 20 ms before `SD_ACTIVATE` goes HIGH (§5, §13.1). |
| `InputStyle::AdcLadders` + `adcLadders` table | 8 keys on two ADC ladders (`IO1`, `IO4`). Readings that are not near a clean level are ignored; software debounce (§9.1). |
| `chargeLadder`: analog charge-status decoder | `USB_STAT` (`IO9`) is a 1 MΩ-class ladder. Windows: >2.6 V idle, 1.80–2.60 V on battery, 0.80–1.35 V charging, 0.35–0.70 V complete. Read ≤1 Hz after a 0.5 s settle, no pulls. "Complete" only when stable, because of the no-battery blink (§3.7, §13.1). |
| `PowerConfig::lowBatteryCutoffMv` | Firmware must sleep well before ~3.3 V; the DW01A 2.4 V cutoff is a last resort (§3.5). |
| `FrontlightConfig`: `colorSelectGpio`/`colorSelectWarmHigh`, `enablePulseUs`, `offDwellMs`, `monitorAdc`/`monitorScaleX1000`/`monitorTripMv` | `ADIM` is also the enable: LOW for at least 3 ms (clears a latched OVP), then a HIGH of at least 100 µs, then the PWM carrier; LOW for more than 2.5 ms shuts down. | `FrontlightConfig`: `loadProbeWindowMs`, `loadProbePeriodMs`, `railSafeV`; `FrontlightManager::probing()` | The light may not be fitted, and nothing sees a load without enabling the boost: sample `LED_MONIT` every 20 ms for 500 ms after the enable, on the monitor timer so the caller does not wait, and turn the light off on a reading above the trip (§13.1). | `SharedAdc.h`: one recursive lock around every SDK ADC read | The LED monitor reads `IO2` on the esp_timer task while the main loop reads the ladders (`IO1`/`IO4`), `BAT_MONIT` (`IO8`) and `USB_STAT` (`IO9`). Arduino's oneshot read only try-locks the unit and returns 0 to the loser. |
| `TouchConfig`: `optional`, `resetPulseMs`/`resetSettleMs`, `fallbackController`/`fallbackAddr`, `hibernateInSleep` | Touch is fitted only on -T01C/-FT01C panels (§8). | `PowerConfig::cutoffRadioAllowanceMv`, `BatteryMonitor::isBelowCutoff(..., radioOn)` | `BAT_MONIT` reads `P+` behind 0.24-0.35 Ω (§3.6), so it reads low under Wi-Fi load. The cutoff used to be skipped whenever Wi-Fi was on. |
| `PowerConfig::firmwareUpdateMinMv` | A firmware write that browns out near empty (§3.5 headroom) is worse than no update. |
| `PowerConfig::awakeCeilingMin`, `PowerConfig::radioOffWhenIdle` | There is no hardware off (§3.5): a network screen or a Never timeout left open on battery empties the cell overnight at tens of mA. |
| `PowerConfig::wakeNoInputTimeoutS`, `storageErrorSleepS`, `awakeInputCapMin` | A pocket press that passes the hold check, a missing card, or a desktop polling a mounted WebDAV share would otherwise keep the board awake for a whole timeout or longer. |

| `PowerConfig::noChargeableCellNotice`, `HalPowerManager::noChargeableCell()` | With no cell, or one too flat for the charger to start (§3.3), USB runs the board and `P+` reads below 2.5 V, or `USB_STAT` shows the charger's no-battery blink: a percentage or a charge state would be wrong, so the UI says there is no cell to charge. |
| `PowerManager::sleepPanelWithoutDriver()` (SSD1677, and with the display-probe policy UC8279/UC8179), `InputManager::resetAndHibernateTouch()`, `holdTouchIntForSleep()` | The panel and touch sit on the always-on 3V3 (§6.1, §8), and nothing resets them after a crash; S3 drops a digital pad's hold at the wake, which a GT911's INT needs. |
| `InputManager::adcLadderContact()` | The idle poll every 10 ms needs only "released or not", not the 16× oversampled decode. |
| `SensorsConfig::rtcFallbackType`/`rtcFallbackAddr` | Either `U13` DS3231MZ (0x68) or `U14` RV-8263-C7 (0x51) is fitted (§10). |
| `SensorsConfig::rtcResyncWhenInvalid` | No backup cell: time is lost with the battery, so fetch it again whenever the RTC reports it invalid (§10). |

## Defaults chosen for the first build

These follow the plan's recommendations and can be changed:

- **Front light: compiled in** (`FREEINK_CAP_FRONTLIGHT=1`, `FREEINK_CAP_WARMLIGHT=1` in `[silkscreen] frontlight_flags`), for a bonded panel light on `J3` or an external string on `J6`. `IO42` (ADIM) and `IO40` (COLOR_SEL) are parked LOW at boot and through sleep either way; the light code drives them only while awake. A board with no light keeps the same image: the boost runs only when the user switches the light on, and the switch-on probe then finds no load, says so and stays dark (below). An unloaded enable is safe on the standard build (U10 latches off at its OVP, §13.1) but avoidable, so a board that will never have a light may still drop it with `[silkscreen]` / `frontlight_flags =` in `platformio.local.ini`.
- **Front-light enable:** `IO42` dark (LOW, plain GPIO) for at least 3 ms, `COLOR_SEL` set while it is LOW, `IO42` HIGH for 150 µs as a plain GPIO, then the 25 kHz / 10-bit LEDC carrier at the target duty. A brightness change only changes the duty. Off: duty 0, `IO42` LOW, `COLOR_SEL` back to LOW once dark for 3 ms. Never `gpio_reset_pin` on either pin.
- **Warm/cool is a fixed choice**, not a blend: warm (`COLOR_SEL` HIGH) at warmth ≥50%, cool below (§7: blending is a qualification item). A change while lit is a full off/on cycle (≥3 ms dark, so the enable pulse repeats).
- **Front-light over-voltage trip at 23 V** on `LED_SW` (`SILKSCREEN_FRONTLIGHT_TRIP_MV`, 23000 mV; must stay below the TPS923610's 24.25 V minimum OVP, checked by a `static_assert`). The same level serves the bonded ~15 V panel light and a `J6` string of up to 22 V. `LED_MONIT` is read every 100 ms only while lit (V = mV × 9.333). A trip takes `ADIM` LOW and latches a fault; the main loop then switches the light off and clears the saved Frontlight preference, so no wake, restart or power cycle retries it. It stays off until the user switches it on again. A trip leaves `C9` near the OVP level, as an open-load enable does, and HARDWARE.md §13.1 reads a reading above the trip as no light connected, so the reader shows the same "No front light detected. Wait about 10 s before connecting a light." popup.
- **Front-light load probe** (`loadProbeWindowMs` 500, `loadProbePeriodMs` 20, `railSafeV` 15; `FREEINK_CAP_FRONTLIGHT_PROBE`). Only a user action (switching the light on, a colour change while lit) or Restore Light on Wake enables the boost, and a silent restart replays a light that was already on (gated by `restoreAllowed()` like the restore); nothing probes by itself at a cold boot or a wake. After each enable pulse `LED_MONIT` is read every 20 ms for 500 ms on the monitor's timer (under the shared ADC lock), then every 100 ms as before. An open string drives `LED_SW` to U10's OVP within a few ms, and the 10.7 ms `LED_MONIT` RC crosses the 23 V trip 25-30 ms later. Through U10's OVP retries `LED_SW` sags only slowly (`C9` through `R39`/`R41`), so it stays above the trip far longer than the 20 ms between readings, and any one reading above it decides; the 500 ms window leaves room for U10's soft-start into no load, which is not in hand (B8 scopes it). A reading above the trip takes `ADIM` LOW at once (U10 shuts down 2.5 ms later, which clears its latch; the next enable waits the 3 ms dwell) and is a "no load" result for the string `COLOR_SEL` selects, kept apart from an in-use trip.
  - With a colour select the other string is tried in the same switch-on. If it lights, the first is recorded missing and warmth lights the other string; the light panel's warmth row says "Cool light only" or "Warm light only" and ignores input. The SDK's record keeps the mark until a cold boot, a later no-light result included, and the reader saves its warmth on the string that is there (0 or 100 %), so a cold boot and Restore Light on Wake select that string too. Only the user changing the warmth after a cold boot (before that the warmth stays pinned) selects the missing one again, and that switch-on probes it.
  - If nothing lights, the light is off and the SDK's record says no light. The reader says "No front light detected. Wait about 10 s before connecting a light." (a popup; in the light panel, a line under the brightness row), saves the light as off, and keeps the control: switching it on again is the retry. In the light panel the brightness slider and steps then only set the level, so a drag or a held key does not run the probe on every step; the lamp toggle is the retry.
  - A Restore Light on Wake (or a silent restart's replay) that finds no light shows the same popup once the first screen is up, and keeps the saved "on": the record stops later wakes from restoring, and a cold boot tries once again.
  - The record sits in RTC memory (8 bytes) and is trusted after a deep-sleep wake or a software restart only. Restore Light on Wake asks it first, so a wake never restores into nothing; a cold boot clears it, so a restore may try once.
  - After any trip, `C9` stays near the OVP level, so `COLOR_SEL` moves only once `LED_SW` reads 15 V or less (the bonded string's forward voltage at 13 mA), waited for at most 4 s: before a second try, on the monitor timer while dark, and in `prepareForSleep()`.
  - No switch-on holds its caller: the call that lit the light returns at once, and `FrontlightManager::probing()` stays true until the switch-on has decided. That is the 500 ms window when the first string lights. One that falls back to the other string adds the rail wait (about 1-3 s, at most 4 s) and a second window, both on the timer; a no-light result comes typically 1-3 s after the switch-on, at most about 4.5 s. Meanwhile the light reads on: a brightness change applies at once and a colour change once it has decided, and the menu checkboxes and the light panel follow the result when it arrives, then the popup (or the panel's note). A restore in `Frontlight.begin()` no longer delays the first paint: on a board with no light its popup comes a few seconds after boot. If the rail has not fallen within 4 s, the second string is not tried: the light is off as after a trip (the same popup, and the light saved as off), and it is not a no-light result.
- **The light goes dark before every software restart** (a shutdown handler registered by `HalFrontlight::begin()`): `ADIM` LOW, 3 ms, then `COLOR_SEL` LOW, before the reset releases both pads.
- **Keys reach the light panel:** with keys and a light, Settings > Display > Frontlight opens it. Left/Right set the brightness, Confirm switches the light, Up/Down pick warm or cool, Back closes it.
- **Panel controller: probed.** Good Display GDEQ0426T82 panels carry an SSD1677; the custom 4.26" panel a UC8279D, same 800x480 and orientation. At every cold boot, before `display.begin()`, the SDK probe resets the panel and reads its VER/FLG registers half-duplex on SDI, both passes with the vendor's 50 ms reset (about 115 ms with an SSD1677 and 170 ms with a UC8279; an UltraChip part answers, an SSD1677 only by elimination). An SSD1677 never drives the FLG read, so a FLG driven the same on both passes is an UltraChip answer even when VER reads blank. Any UltraChip answer runs the UC8279 driver (the X4 Pro's `Uc8279X4Driver`, its waveforms and LUTs unchanged); its LUT_VER (VER byte 2) becomes the driver variant, and an id the driver does not know gets its default tables, both logged. The UC8179 driver is not linked. A conclusive verdict is kept in RTC memory and reused on a deep-sleep wake with no probe; any other reset probes again, and nothing goes to NVS, so a panel swapped with the power off is always found. Deep sleep is not "power off": 3V3 stays live, so a swap means disconnecting the cell and USB. As a guard, the wake's first panel reset (the driver's own) reads `BUSY`: a UC8279 idles `BUSY_N` HIGH and an SSD1677 idles `BUSY` LOW, and a level that stays wrong for 300 ms drops the cached verdict and restarts, which probes. A UC `BUSY_N` wait also gives up after 60 s and drops the verdict. An inconclusive probe runs as SSD1677 and is not kept. The log shows `Panel controller <name> (<how>): VER .. FLG .. variant ..`. `[silkscreen] display_flags = -DSILKSCREEN_DISPLAY_CONTROLLER=uc8279` (or `ssd1677`) in `platformio.local.ini` forces the controller and skips the probe.
- **BUSY pull by controller:** the internal pull-down for an SSD1677's active-high `BUSY`, the pull-up for a UC8279's active-low `BUSY_N`, awake only; both are off before deep sleep (IO48 is never held).
- **Reader overlay:** Silkscreen's panels are X4-class glass (`x4ClassPanel`), so the reader treats them as the X4 (`xteinkClassPanel()`: closing an overlay re-renders the page to restore its gray levels) whenever the driver for the probed controller runs the grayscale pass.
- **`viewableInsets` `{0,0,0,0}`:** every measured case window is the active area plus 0.5-0.7 mm.
- **SDMMC at 20 MHz**, 4-bit. Try 40 MHz only after the bring-up SD tests pass with Wi-Fi and display refresh overlapping.
- **Low-battery cutoff at 3400 mV** on `P+`: 16× averaged readings once a second, 3 consecutive at or below the cutoff, never while `USB_STAT` reports external power (idle, charging, complete, no-battery blink) and never on a reading below 2.5 V (no cell). While `USB_STAT` is still unknown, a reading above 2.5 V proves a cell. With Wi-Fi on the threshold is 100 mV lower (3300 mV) for the `P+` sag under radio load (0.24-0.35 Ω × 100-300 mA, §3.6), and the sleep entry turns Wi-Fi off. Also checked at boot, before SD and the panel: a normal boot pays for one reading, and only a reading within 100 mV of the cutoff waits for the divider and ladder to settle. A cutoff at boot after anything but a deep-sleep wake first begins the panel without a refresh and sends its deep-sleep command, since no sleep entry did. Web uploads, the web server's device-side fetch (`/api/fetch`) and relay (`/api/relay`), every `HttpDownloader` transfer (the OPDS feed and books, plugin-catalog, font and font-list downloads, the OTA check and download), and the plugin event drains block the loop, so they check the same (latched) cutoff and abort; the next loop pass sleeps. `HttpDownloader` checks it in `fetchResumable()`'s abort predicate, which runs in every wait loop: its progress callbacks run only when bytes arrive, and a stalled body is retried. A sleep entry at the cutoff queues the plugin events but delivers none (no Wi-Fi join, no drain), so they wait for the next online session. A `USB_STAT` reading stuck outside every window for 30 s drops the last decoded state (and USB presence reads "not connected"), and Charging/Complete with `P+` at or below the cutoff and not rising for 5 min (read once a minute) is treated as on battery.
- **No chargeable cell on USB** (`noChargeableCellNotice`). While `USB_STAT` shows the charger's no-battery blink (the charger then holds `P+` between its recharge threshold and 4.2 V, so `P+` cannot show it), or on external power with `P+` below 2.5 V (a 4-sample average, read at most every 1.5 s, and cleared only at 2.6 V, so a flat cell charging up through 2.5 V does not flip it), there is no cell, or one too flat for the charger to start. The header and the reader's status bar then show "No battery" (`STR_NO_BATTERY`, short enough for the header beside a centred clock and for the status bar beside its clock and progress) in place of the percentage, with an empty glyph and no charging bolt (`BaseTheme::batteryLabel()`; other boards' labels are unchanged). Check it on the device in portrait: RoundedRaff with the header clock, and the status bar with the clock left and right.
- **Firmware writes need 3.6 V on battery** (`firmwareUpdateMinMv`; 3.5 V as read with Wi-Fi on, the same 100 mV allowance). OTA and the SD firmware update refuse below it unless `USB_STAT` shows external power, with "Battery too low, connect USB" (`STR_BATTERY_TOO_LOW_FOR_UPDATE`). The SD flow checks again right before the write.
- **Wake: power button only** (`IO18`, ext1 ANY_HIGH via `PowerManager::armPowerButtonWakeup`; no RTC_PERIPH domain needed). `scripts/check_sleep_wake_sources.sh` fails if another wake source, light sleep, a power-domain override or a second `esp_deep_sleep_start()` appears in `src/`, `lib/` or the SDK.
- **Sleep-current target:** ≈58 µA typical without touch (≈95 µA by datasheet maxima), ≈113 µA with an FT6336U tail hibernated. The itemized budget, the per-pin sleep states and the measurement procedure are in [POWER.md](POWER.md).
- **A held power button at sleep entry:** wait at most 5 s for the release (`releaseWaitMaxMs`), then sleep with ext1 ANY_LOW on `IO18` (wake on release). That boot sleeps again at once (`takeReleaseWake()`, first thing in `setup()`, before any peripheral starts).
- **Sleep-or-boot is decided right after the wake-hold check** (`earlyWakeDecision`), before touch, the RTC, SD, the settings, the light, the panel and Wi-Fi. Short Power Button Press lives on SD, so every sleep entry with the settings loaded leaves the wake rule (a click wakes, or the hold is required) in RTC memory. With no rule there (the first wake after a power-on), the decision waits for the settings as before, and if SD then fails, an unverified wake still sleeps. The touch probe runs after the decision.
- **3 abnormal resets in a row** (panic, watchdog, CPU lockup, brown-out, or an aborted sleep entry; `abnormalResetLimit`) and the next boot sleeps at once, with no SD, radio, display driver or touch driver. Without their drivers, the panel controller is probed, then the panel gets a reset pulse (analog off) and its bit-banged deep sleep (SSD1677 `0x10`/`0x03`, UC8279 `0x07`/`0xA5`), and an FT6336U gets a reset and one hibernate write. A power-button wake starts a new count, and so does 60 s of uptime.
- **Awake ceiling on battery: 15 min** (`awakeCeilingMin`), or the user's sleep timeout when that is longer (`HalPowerManager::awakeCeilingMs()`; Never counts as 15 min), with no key, touch or tilt input and no web-server request or WebSocket frame. OPTIONS, HEAD, PROPFIND, LOCK and UNLOCK do not count: an OS polls a mounted WebDAV share with them. Nor does `GET /api/plugin-jobs/claim`, which any open page hosting a plugin action sends every 2.5 s whether or not a job is queued; a claimed job counts. It ends network screens, the keyboard, OTA and a Never timeout, and never cuts short a timeout the user chose. A sleep timeout the user set still governs every other screen. **60 min with no input** ends any screen on battery, client traffic or not (`awakeInputCapMin`). The plugin event drains block the loop, so they stop at the ceiling or the cap themselves (`HalPowerManager::backgroundNetworkMustStop()`; their events stay queued), and a sleep entry past either delivers no plugin events.
- **After a power-button wake with no input: sleep after 3 min on battery** (`wakeNoInputTimeoutS`, WK-02). The wake press's own release does not count as input, and a screen that holds auto-sleep off keeps it off. Nobody is at the device, so that sleep queues no `sleep.enter`, joins no Wi-Fi and delivers no plugin event. **The SD-card error screen sleeps after 60 s on battery** (`storageErrorSleepS`).
- **Wi-Fi off when a network screen's work ends** (`radioOffWhenIdle`): OTA, Clock Sync and KOReader Auth switch the radio off at their result screens and stop spinning the loop; KOReader Sync switches it off on a failure and drops to modem sleep on the result screens that can still upload. Font Download keeps the radio for its lists but spins only while loading or downloading, and after a download refreshes the idle timer once instead of holding auto-sleep off. Clear Cache spins only while clearing. Leaving any of them still restarts to clear the heap. A plugin catalog keeps the radio while it is open, like the OPDS browser, but Back to the plugin picker switches it off (the next pick joins again), and so does the Wi-Fi picker the reader opens to sync a loan's clock when it is cancelled or its join or sync fails.
- **USB Drive ends when the cable is pulled on battery:** once `USB_STAT` has shown external power in the session, 3 s of "on battery" ends the session and restarts to Home.
- **Touch: compiled in, probed at boot.** `TP_RST` (`IO11`) LOW for ≥5 ms, then ≥300 ms before the first transaction; then the FT6336U at 0x38 (FT5x06 path: `INT` gated polling, `IO41` with the MCU pull-up while awake). The probe reads the chip id (`0xA3`) before its first write and accepts only a FocalTech one (0x06, 0x36, 0x64; `requireFocalTechId`): a J6 device at 0x38 is left alone, and the refusal is kept across deep sleep like an absent panel. The reader logs a refusal (`Device at 0x38 is not a FocalTech touch controller (chip id 0x..)`). A GT911 at 0x5D/0x14 (its `INT`-strap reset) is tried next only in a build with `[silkscreen] touch_flags = -DSILKSCREEN_TOUCH_ALT_JUMPERS=1` (alternate J4 jumpers), so a default build never drives `IO41`. With nothing found, the board is touchless for the session (`ACTIVE.touch.controller = None`, so `BoardConfig::hasTouch()` and `HalGPIO::hasTouch()` agree). The result is kept in RTC memory: a deep-sleep wake skips the probe of an absent panel and starts with the controller found before; a cold boot probes again. Touch runs at the sensor-bus clock (100 kHz). The orientation (`swapXY`, `flipY`) is a guess until the corners are mapped (B9).
- **Touch in sleep.** `TP_RST` is held HIGH at boot and through sleep: an FT6336U's ~3 kΩ `RSTN` pull-up draws ~1.1 mA from a LOW pin, and a reset leaves hibernate. At every sleep entry after the probe (menu, auto-sleep, the awake ceiling, the battery cutoff), an FT6336U gets hibernate (`0xA5 = 0x03`); if it does not ACK (its Monitor mode closes the serial port), it is reset (≥5 ms, then ≥300 ms) and the write is repeated once. `TP_INT` stays unheld for an FT6336U. A GT911 gets `INT` LOW ≥5 ms, `0x8040 = 0x05`, ≥58 ms, then `INT` held LOW through sleep, released at the next boot before its reset. **When no controller answered the probe**, one hibernate write still goes to 0x38 (about 0.1 ms; a NACK with no tail), in case a tail is fitted but missed the probe; there is no reset retry and no GT911 `INT` hold, since holding `INT` LOW would wake an FT6336U. A tail that misses the probe and is in Monitor mode therefore stays at ~220 µA until the next cold boot. A ghost wake and a release wake sleep before the probe and send an FT6336U nothing: it is still as the last sleep entry left it. A GT911 is not, because S3 drops the `INT` hold at the wake: with the probe cached as GT911, `INT` is driven LOW again as soon as the keys are set up, a ghost wake re-sends its sleep command, and a release wake re-holds `INT` LOW. The abnormal-reset sleep resets an FT6336U and sends one hibernate write once its chip id reads back, since nothing after the crash put it to sleep. An alternate-jumper build never pulses `TP_RST` there (a reset without the `INT` strap restarts a GT911 awake): it tries the FocalTech hibernate without it, then the GT911 sleep command at 0x5D and 0x14, and holds `INT` LOW either way. With `requireFocalTechId`, a sleep write to a controller the probe did not find first reads its chip id, and a device the probe refused gets none: a genuine tail refused by the id check is never hibernated and draws its Monitor current (about 220 µA, about 165 µA over hibernate) in every sleep, so B9's `touch_id=ok:64` is a gate before release. A GT911 tail on the alternate jumpers running an image built without `-DSILKSCREEN_TOUCH_ALT_JUMPERS=1` is reset awake by the FT probe (at 0x14) and never put to sleep: about 3.3 mA in every deep sleep, which P2 reports as `touch_not_probed`. A Silkscreen build with `-DFREEINK_CAP_TOUCH=0` fails a `static_assert`, because it could not send the sleep command to a fitted tail.
- **I2C bus.** `SensorsConfig::i2cHz` (100 kHz) is the one clock: every driver on `IO38`/`IO39` starts the bus at it, whichever starts first. The first start in a boot frees a bus a slave holds LOW (9 `SCL` clocks, then a STOP). Before deep sleep, after the touch sleep command, `Wire.end()` (which waits for a transfer in flight on another task), then `SDA`/`SCL` are left unheld inputs with no pulls, and a stuck bus is clocked free, so the 2.2 kΩ pull-ups keep both HIGH.
- **Keys with touch.** The keys stay the primary input. With touch fitted, the key hints, the front-button remap, "Orient Front Buttons", "Short Back to File Browser", the key help lines and the keyboard cursor stay, alongside the touch UI (`TouchConfig::buttonsAlongsideTouch`). The Sunlight Fading Fix row stays too, whether or not the touch probe found a tail: it depends on the panel, which is the same either way.
- **RTC:** DS3231MZ at 0x68 (`U13`, standard build), falling back to RV-8263-C7 at 0x51 (`U14`). Before its control and status registers are written, 0x68 must show the DS3231 register pattern (`rtcIdentityCheck`: the bits the datasheet fixes at 0, a day of week of 1-7, BCD seconds and minutes; read again after 20 ms on a mismatch). A device without it is logged (`Device at 0x68 is not the RTC`) and left alone, and 0x51 is tried. EN32KHZ is cleared (or the RV-8263 CLKOUT switched off), and the time is fetched from NTP on a Wi-Fi connection whenever the RTC reports it lost.
- **Key ladders checked for their pull-up** (`ladderPresenceProbe`). At every reset but a deep-sleep wake, before the keys are read, each ladder pin is read with the internal pull-down and then the pull-up (about 2 ms each, both off afterwards). A pin that follows both from rail to rail (≤400 mV, ≥2600 mV) has no pull-up fitted and is switched off for the session, so it reports no phantom keys (which would hold the board awake, turn a power hold into a screenshot or start SD recovery at a wake); the log says `Key ladder IO4 has no pull-up ...`. A fitted ladder cannot pass, released or with a key held. The result is kept in RTC memory (5 bytes) for deep-sleep wakes.
- **Power button idle check** (`powerPinIdleCheck`). At every reset but a deep-sleep wake, right after the release-wake check and before anything can arm a wake, `IO18` is read on the ADC (ADC2, with the radio off): four 8-sample readings over 15 ms. If all four sit between the logic levels (R36 and R72 both fitted, about 1.76 V), the pin is switched off for the session: every sleep then arms no wake source and holds the pad with its input off, so the reset button (SW11) starts the board. The reader shows "Power button fault: its input idles at 1.7 V ..." (`STR_POWER_BUTTON_FAULT`), stays on it while `USB_STAT` shows external power (so the board can still be flashed), and sleeps on the cell. The test firmware boots on and reports it in P1 and T3. A boot that finds the button held through the whole 15 ms check (`pwr_idle=high`, "held at boot") cannot tell, and deep-sleep wakes do not check, so such a fault is caught at the next reset with the button released.
- **Flash/PSRAM:** `esp32-s3-devkitc1-n16r8`, `dio_opi`. This is the same prebuilt core as X4 Pro, with TinyUSB MSC for USB Drive mode. 16 MB, two OTA slots (`partitions.csv`).
- **No DevKitC bench env.** The first target is the real board.
- **OTA:** unchanged. It looks for a `-silkscreen` asset in upstream releases, finds none, and reports no update.

What the merges changed for Silkscreen:

- **The profile is written with designated initializers.** Upstream appends fields to `BoardProfile` and its sub-structs and fills its own profiles positionally.
  - In each struct, upstream's fields come first, in upstream's order, and the Silkscreen fields follow them. `HapticConfig haptic` therefore sits right after `i2cFrontlight`, ahead of `parkedPins`, `adcLadders`, `chargeLadder` and `displayProbe`, so `METALIO_EINK4`'s positional initializer, which ends in its haptic values, still lines up.
  - `SILKSCREEN`, and every sub-struct it sets, names each member in declaration order, so a field upstream appends cannot shift its values. A member left out takes its default, which is why every pin is named.
  - The designated profile compiles to the same object as the old positional one with `haptic` defaulted (404 bytes, xtensa g++ 14.2), in the default build, with `SILKSCREEN_DISPLAY_CONTROLLER=uc8279` and with `SILKSCREEN_TOUCH_ALT_JUMPERS=1`.
- **`ResumableFetch` keeps credentials on the starting origin.** `fetchResumable()`'s configure callback now takes `(SecureHttpClient&, bool sameOrigin)`. `HttpDownloader` adds its Basic auth and headers, and the web server's `/api/fetch` a plugin's headers, only while `sameOrigin` is true, so a redirect to another host or to plain http gets neither. This is upstream's code and the same on every board. The low-battery cutoff still ends these transfers: `/api/fetch` and `HttpDownloader` (the OPDS feed and books, plugin-catalog, font and font-list downloads, OTA) return `lowBatteryCutoffTripped()` from their `shouldAbort`, which `fetchResumable()` polls in every wait loop. The cancel flag the progress callbacks set is not enough on its own: they run only when bytes arrive, and `fetchResumable()` retries a stalled body with Range requests (up to 3 attempts in a row with no progress, 60 s each).
- **The plugin system keeps to the drain rules.** Upstream's SD-card plugins add network work that blocks the loop: event drains at a Wi-Fi station join, when the web server starts and at sleep entry; `/api/fetch` and `/api/relay`; catalog downloads; and the catalog's sign-in poll.
  - On Silkscreen, each of these stops at the low-battery cutoff. The transfers abort from their abort predicates or callbacks. The sign-in poll runs from `loop()`, one bounded request at a time, so the loop's own check runs between polls. The drains also stop at the awake ceiling (15 min, or the sleep timeout if longer) and the 60-min input cap (`HalPowerManager::backgroundNetworkMustStop()`), and leave their events queued.
  - A sleep entry past any of the three delivers nothing, and neither does a WK-02 re-sleep (a power-button wake that got no input), which also queues no `sleep.enter`.
  - The idle plugin-job poll does not count as client traffic.
  - The radio goes off on the plugin picker and when the loan-clock sync is cancelled or fails.
  - The front light goes dark at the start of `enterDeepSleep()`, before the sleep entry's plugin delivery, not at the end of the sleep path.
  - Only the `SILKSCREEN` profile sets the fields involved, so other boards behave as upstream. The rules and their cost are in [POWER.md](POWER.md#3-firmware-rules-and-where-they-live) (AW-01, AW-02, BAT-01) and [§5](POWER.md#5-the-awake-idle-tail). The test firmware leaves the plugin system and the loan clock (`TrustedTime`) out ([TEST-SUITE.md](TEST-SUITE.md#how-the-test-firmware-differs-from-the-reader)).
- **Metalio E-Ink 4 shares the SDK files with Silkscreen.** Its code runs only on Metalio, and the Silkscreen code only from profile data and `FREEINK_CAP_*` flags that Metalio does not set.
  - `Board::MetalioEInk4` keeps upstream's value, and `Board::Silkscreen` follows it; nothing stores the value. `MAX_FRAMEBUFFER_BYTES` counts both boards, and `DEFAULT_DEVICE` picks `SILKSCREEN` first, then `METALIO_EINK4`.
  - `holdPowerRails()` and `InputManager::begin()` run Metalio's `ensureBooted()` first, as upstream does, then the parked pins and the SDMMC park. Each step does nothing on the other board.
  - Upstream's CST816S start is in `InputManager::beginTouchController()`, and the optional probe with its fallback stays in `beginTouch()`. Metalio's touch is neither optional nor has a fallback, so it still reaches `beginCst816s()` directly.
  - `SdmmcBlockDevice::begin()` takes the parked mount (`parkLowWhenOff`) before Metalio's DAT3 pull-up, and Metalio still reaches the pull-up.
  - Upstream's SSD1677 changes are `Ssd1677Config` fields that default off (`blackPulseClean`, `writeSecondUpdateControlByte`, `restoreInternalTemperature`, `factoryGrayLut`), and Silkscreen runs the default config. `overlayGrayscale` defaults on, as before.
  - Silkscreen does not build Metalio's haptic, audio, microphone, SC7A20H or BLE code: it sits behind `FREEINK_DEVICE_METALIO_EINK4` or an `imuType`, or is not in `lib_deps`.
  - CrossPoint has no Metalio env, and `src/network/FirmwareBoardTag.cpp` names no Metalio board, so the reader cannot be built for it, here or upstream. A scratch env that builds every SDK source for Metalio compiles; its only error is that missing board tag.
- **The "Links and footnotes" label** is upstream's and needs nothing for Silkscreen. The Silkscreen strings in `english.yaml` merged unchanged.

## What this port does differently

The first port was audited item by item against HARDWARE.md. What changed:

| First port | This port |
|---|---|
| USB detect: `USB_STAT` outside 1700–2250 mV, read every loop | Windows from §13.1 (on battery 1.80–2.60 V). Sampled ≤1 Hz after settle and debounced. `ST` is not treated as proof of USB. |
| `INPUT_PULLDOWN` on the power button, `INPUT_PULLUP` on the charge pin | No internal pulls on externally biased pins |
| Internal SDMMC pull-ups plus explicit `gpio_pullup_en`; 80 ms gate pulse after slot init | No internal pulls. The bus is parked LOW before gating off, and there is a real power cycle before init. |
| Frontlight: COLOR_SEL as a warmth PWM channel, even at brightness 0; no enable pulse | Static COLOR_SEL, switched only with ADIM dark and LOW whenever the light is off; ≥3 ms dark, 150 µs enable pulse, then the carrier; LED_MONIT over-voltage trip with a latched fault; a load probe at each switch-on the user asks for, per string, with its result kept across deep sleep. The light is restored only after a verified wake and handed over (dark, LEDC detached) before sleep. |
| Ladder pins and thresholds hard-coded (`IO1/4/8/9/2`) in InputManager | Data-driven ladder table in the profile; ignores non-clean levels; 2-sample debounce |
| `isSilkscreen()` branches in SDK feature files | None; all board data |
| UC8279 forcing, SDMMC 400 kHz / 1-bit bench knobs, 8 MB single-slot partitions, `default_envs = silkscreen, devkitc` | The controller is probed at every cold boot (SSD1677 or UC8279); forcing it is an opt-in build override. None of the other knobs. |
| No low-battery shutdown | Cutoff at 3.4 V on battery |
| SDK commits on no remote; `.gitmodules` on Free-Ink `main` | `.gitmodules` on the fork's `silkscreen` branch |

1. **B0 - Power, no flash** (BRING_UP §1, §2, §3.1, §3.2). After the loupe and the unpowered meter checks (BRING_UP §1, §2): no panel, no card, `J3` unplugged, current-limited USB. 3V3 present; `IO42` ≈ 0 V; `IO10` HIGH, so `SD_VDD` ≈ 0 V. The USB-Serial-JTAG port enumerates. Scope `USB_VBUS` at a hot-plug: at most 6.0 V (BRING_UP §3.2).
2. **B1 - Boot safety and console** (BRING_UP §9: the power button, the UART). Flash. The log shows `Device: silkscreen` and about 8 MB PSRAM, and P1 shows the power button idling low and both key ladders fitted (boot with POWER released: a button held through the 15 ms idle check reads `high`, and a fault is then caught only at the next reset). Scope `IO14`/`IO13` from EN release: CS is HIGH before the first SCLK edge. `IO42`, `IO40` LOW; `IO10` HIGH. A power-button press is logged; `IO18` at `R76` pad 1 reads 0 V idle and ≈ 3.0 V pressed (1.76 V idle means `R36` and `R72` are both fitted).
3. **B2 - Display** (BRING_UP §8). Attach the GDEQ0426T82. The log and P1 show `Panel controller SSD1677 (probed)`, with no UltraChip answer. FULL/HALF/FAST refreshes and the grayscale anti-aliasing pass are clean at 20 MHz SPI. Check orientation (text upright relative to the bottom keys) and that the `{0,0,0,0}` `viewableInsets` fit the case window. Check night-mode ghosting. With T4's scope loop running each refresh mode back to back, scope the panel's rails (BRING_UP §8, 10x probes): `PREVGH`/`PREVGL` about ±22 V, `VSH1`/`VSL` about ±15 V, and `GDR` and `RESE` clean, with `RESE` peaks well under 2.4 V. Then bring up the custom UC8279D panel, in this order:
    - **Probe verdict and IDs.** The log and P1 show `Panel controller UC8279 (probed)` with its VER, FLG and LUT_VER (VER byte 2, also the driver variant). Keep P1's `action=panel` row, which carries the 48 MTP bytes.
      - After a sleep and a wake, P1 shows the same verdict, kept from the probe before the sleep (`source=cached`).
      - Swap the two panels with the power off, which on this board means the cell and USB disconnected (deep sleep keeps 3V3 live): the next cold boot finds the other one.
      - Do not test the wake guard (`BUSY stays ... after the reset`) by swapping the flex with the cell in: hot-plugging the panel risks it. The guard only limits the damage of a swap made that way.
      - An inconclusive probe runs as SSD1677, and P1 fails `panel`. Force the controller with `display_flags` and report the log.
    - **Geometry.** `Uc8279X4Driver` addresses the panel as the X4 Pro's: TRES 800×600 with the 480 visible rows from gate 120, PSR `0x37`/`0x4D`, PLL `0x0E`.
      - The MTP dump holds the panel's own programmed TRES. Compare it before judging placement in T7.
      - If it differs, give Silkscreen its own `Uc8279X4Config` (`tresHeight`, `gateOffset`, PSR, PLL) through `-DFREEINK_UC8279_X4_CONFIG`.
    - **BUSY polarity.** The UC8279's `BUSY_N` is LOW while busy and idles HIGH, with the internal pull-up while awake.
      - T4's refresh times must be real waits (hundreds of ms for FULL), not 0 ms (BUSY read the wrong way) and not a hang.
      - Scope `IO48`: LOW through a FULL refresh.
      - With the flex unplugged, the boot must not hang.
      - A UC8279 driven as an SSD1677 (a wrong verdict) shows waits that end at once or time out, and a blank or garbled panel. The SSD1677 soft reset `0x12` is a UC refresh command. A UC8279D that drives FLG the same on both passes is taken as UltraChip even with VER all `FF` or all `00` and a blank MTP (its variant is then `FF` or `00`, logged as unknown, with the default tables), so report the log's VER, FLG and MTP whatever the verdict.
    - **Charge pump.** Silkscreen's pump (L1 47 µH, R14 2.2 Ω) is sized to the SSD1677 reference. T4 and T5 must be clean in every mode, with no fading or speckle.
    - **Deep-sleep current.** The UC8279 sleeps with power-off, then DSLP `0x07`/`0xA5`. Its sleep current and its `BUSY_N` level in sleep are not in hand: measure both with this panel in B3 and B10.
    - **Waveforms.** The UC8279 driver's waveforms and LUTs were tuned for Xteink panels. Its variant picks the gray tables:
      - `0x02`/`0x03`: the QY tables;
      - `0x67`: OTP only, no gray;
      - anything else: the default `0x68` tables, logged as unknown.

      Judge T4, T5 and T6 on this panel before tuning anything. Keep its T4 times as this panel's baseline, since T4's references are the SSD1677's.
4. **B3 - Sleep and wake** (BRING_UP §6, the firmware state). Sleep and wake from `IO18` repeatedly. No false wakes over 30 minutes. In sleep: `IO47` ≈ 3.3 V (RST not held LOW), `IO14` 3.3 V, `IO12`/`IO13`/`IO21` 0 V, `IO48` ≈ 3.3 V with an SSD1677 panel (`BUSY`, no pull; with the UC8279D panel note the level, which is not in hand), `IO11` 3.3 V (TP_RST HIGH), `IO38`/`IO39` 3.3 V, `IO42`/`IO40` 0 V (including after sleeping with the light on, warm and cool), `IO5`-`IO7`/`IO15`-`IO17` 0 V and `IO10` 3.3 V. Scope `IO47` across a ghost wake: no LOW excursion. `esptool chip_id` works after wake and after an SW11 reset. On a current logger with a release build (the dev env adds a 250 ms USB-serial wait), a short tap (ghost wake) stays awake for about 0.3 s or less, with and without a card. Tape the power button down and trigger a sleep: the current falls to the floor + ~30 µA within ~5 s, and the release gives one short wake before sleeping again.
5. **B4 - SD card** (BRING_UP §9, the SD switch-on). Scope `SD_VDD` at cold boot: below 0.5 V for at least 20 ms with the bus LOW before power-on. Mount within 3 attempts. Copy 200 MB and verify SHA-256. With no card, a clean "SD card error" and the bus left parked. In sleep, `SD_VDD` < 0.5 V and no bus pin HIGH. USB Drive mode in and out. With P3's power cycles (BRING_UP §9), scope `3V3` at `U3.5` as `SD_VDD` switches on: it stays above 3.0 V.
6. **B5 - Buttons** (BRING_UP §9 for the power button, §10 for UP(2) as POWER). T3's boot-checks row shows both ladders fitted; P1 shows their readings with each pull (a fitted ladder reads above about 2.2 V pulled down). Build with `-DFREEINK_ADC_LADDER_TRACE=1` and log mV for every key on USB and on battery. Tune the windows, especially BACK, UP(2) and the released threshold, which sit near the ADC's 2.9 V ceiling. 50 presses each give 50 events, including with Wi-Fi on. Chords decode as §9.1 says or are ignored. T3's hands-off watch also reads `IO18` on every pass (`power_not_low`) and warns when ladder 2 released sits below ladder 1 (`io4_not_top`, `io4_low`).

    With UP(2) as POWER (a cut-down board, or a full one reworked: `R36`/`R73` out, `R72`/`R74` in), set the test firmware's OPT first. T3 then counts `SW7` as POWER on `IO18`, as many times as every other key (on a full-length board `SW10` stays on `IO18` too: press each as many times as every other key, and POWER expects twice that count, `pwr_expect=2x`), and fails `up2_window` if ladder 2's UP(2) window ever fires; `IO18` at `R76` pad 1 reads 0 V idle and ≈ 3.0 V with UP(2) pressed.

    Then check the ladder probe. Its thresholds (at most 400 mV pulled down, at least 2600 mV pulled up) are derived. Use a board built without one ladder's pull-up (`R28`/`C28` off, no side keys), or a spare board with `R28` lifted:
    - P1 shows that ladder `off`, with both floating readings;
    - the log says `Key ladder IO4 has no pull-up`;
    - T3 leaves its keys out;
    - the board sleeps on its timeouts with no phantom keys.

    Report both pairs of readings, fitted and floating, so the thresholds can be set from them.
7. **B6 - Battery and USB_STAT** (BRING_UP §3.3, §4, §5; §9 for the LDO's temperature). Log `IO9`/`IO8` in each state: on battery (~2.20 V), charging (~1.11 V), complete (~0.55 V), charger idle (~3.3 V), and cell pulled on USB (0.55/0.41 V blink must never report "charged"). The on-battery level is unverified on real parts (DESIGN_REVIEW), so re-window if needed. On battery only (BRING_UP §4), T2 stage 1 judges 10 samples since the last change (fewer record INFO, `too_few_samples`): any at or below 1350 mV, the charging or complete band, fails `hw08_clamp` (the unpowered TP4056 clamps the ladder, so the firmware cannot tell the cell from USB; that is the trigger for [POWER.md HW-08](POWER.md#6-hardware-notes-for-a-future-revision)'s `P+` trend check); 1350-2100 mV warns `partial_clamp`, 2300-2600 mV `above_nominal`, and above 2600 mV `st_not_asserting` (`ST` not asserting: check `U2.8`/`R17`). With the cell pulled on USB (BRING_UP §5), T2 stage 5's 12 s capture records the blink's period and duty, or a steady 3.3 V (the charger switched off, also safe). On USB with no cell, T1 and the reader's header say "No battery". Ramp a supply on `J5`: the device sleeps at ~3.40 V with Wi-Fi off, and at ~3.30 V as read on `IO8` with the web server running. With the test firmware's U1 TX bursts on that supply (named as a bench supply), sweep it from 4.20 V down until the reader's cutoff sleeps it (about 3.30 V as read with the radio on; P1 then shows a deep-sleep wake, not `BROWNOUT`), and scope `3V3` at `U3.5` for dips below 3.0 V and resets (BRING_UP §3.3). TX below the cutoff, in the 3.2-3.3 V band where BRING_UP expects the sag, is not covered. A brown-out shows in P1 as `reset=BROWNOUT` only when `P+` is still at about 3.4 V or more as the board reboots; below that the boot cutoff sleeps it first, and only the scope and the ROM's reset line on the UART log show it. On USB, with the board in its case, U2's sustained load runs Wi-Fi, the card and the panel for a thermocouple on `U3` (BRING_UP §9). Log `IO8` with Wi-Fi on and off at one supply voltage to check the 100 mV allowance. Below 3.6 V on battery, OTA and SD flashing refuse. Pull the USB cable during USB Drive on battery: the session ends within ~5 s and the device returns to Home. Leave the web-server screen idle on battery: it sleeps after 15 min.
8. **B7 - RTC** (BRING_UP §9). Probe 0x68: T13 shows the identity check passed and the dump matching the DS3231 pattern. OSF is set after a cell insert and cleared once time is set over NTP. Register `0x0F` bit 3 = 0. Check I2C edges at 400 kHz before raising the bus from 100 kHz.
9. **B8 - Front light** (lit builds only; BRING_UP §7).
    - **Flex map first** (BRING_UP §7.1, LED-12): board unpowered, the flex in `J3`, a floating 1 mA supply ramped to ≤ 16 V from `TP3` (+) to `TP4` (cool) and `TP5` (warm). Each string should glow at ≈13-15 V. If it lights only with the leads swapped, the flex uses the reversed FT01C map: do not answer "J3 panel light" in T9 or T10, and do not switch it on in the reader.
    - **Enable sequence** (load connected). Scope `IO42`: at least 3 ms LOW, then about 150 µs HIGH, then the 25 kHz carrier. COLOR_SEL changes only with ADIM LOW, at least 3 ms after it fell. `LED_MONIT` × 9.33 ≈ 15 V lit. T9's record carries each string's `LED_SW` at 100 % and about 10 % duty and their difference (`vf=`, `dvf=`; BRING_UP §7.2).
    - **Colour change** (BRING_UP §7.3). T9's switch run (Right, lit) changes colour once a second, 10 times each at about 100, 50 and 10 % duty. Scope `TP3` and `COLOR_SEL`: `LED_SW` re-slews by ΔVf within about 350 µs and stays below 23 V, and the light never latches off (the run fails on any trip).
    - **Trip.** Force a trip with the test firmware's T10, which lowers the trip level in RAM for one run and also exercises the switch-on probe. Or build with a temporarily lower `SILKSCREEN_FRONTLIGHT_TRIP_MV` (for example 12000). Do not force it by unplugging the load while lit. Then:
      - the light goes off and the log shows the trip;
      - on the reader image, the "No front light detected" popup with the 10 s advice;
      - it stays off until switched on again, including across a sleep and wake and a Wi-Fi screen's restart.
    - **Detection with no light** (`J3` unplugged, `J6` empty: a safe open-load enable). Switch the light on:
      - the log shows `load probe: ... no load` for each string;
      - the reader shows "No front light detected" with the 10 s advice, and `IO42` stays LOW;
      - the light control stays, and switching on again retries;
      - the light reads on while the switch-on decides: the first string trips inside its window, `C9` falls (about 1-3 s, at most 4 s), then the second string trips too; the screen and the keys stay live, and the message follows the result;
      - in the light panel, dragging the slider or holding a brightness key afterwards changes the level only: the log shows no further `load probe` lines until the lamp toggle.

      The test firmware's T10 step 0 makes the same check opt-in (BRING_UP §7.4): it asks for the driver build, refuses the TPS923611 swap without an SMAJ33A at `D3`, and records the trip time (within 500 ms), `IO42` held LOW, no relight for 2 s and `LED_SW` 10 s later. Scope `LED_MONIT` against the enable: the trip crossing must fall inside the probe's 500 ms window (readings every 20 ms; the TPS923610's soft-start with no load is not in hand). The log's `LED rail down to 15 V after ... ms` times `C9`'s decay after a trip, which the 4 s rail-wait bound and the 10 s connect advice assume to be about its nameplate value. Wait 10 s after an open-load enable before connecting a light.
    - **Restore path.** Leave the light on with Restore Light on Wake on, sleep, unplug the light, and wake:
      - the restore tries once and finds no light: the first screen comes up at once, and "No front light detected" with the 10 s advice follows a few seconds later (typically 1-3 s, at most about 4.5 s);
      - the next wake does not enable the boost (`Frontlight not restored`);
      - a power cycle tries once again, with the same message.
    - **Single-colour strip.** A cool-only `J6` strip at the default warmth lights cool after the rail wait (about 1-3 s), and the warmth row says "Cool light only". The log shows `Warmth saved as 0%`. The warm string is not selected again: not after the strip is unplugged and a switch-on finds no light, and not after a power cycle (the first switch-on lights cool at once).
    - **Trip margin.** With a `J6` 6+6 strip, cold and at full brightness, T9's lit readings and `probe_peak=` must stay clear of the 23 V trip. A strip near 22.3-22.9 V can read as "no load" or as a missing string: report its reading.
    - **Never by itself.** A ghost wake (short tap) must not light the LEDs, and a boot with Restore Light on Wake off never enables the boost (scope `IO42`).
    - **Restart.** Scope `IO42`/`IO40` across a silent restart with the light on warm: `ADIM` falls at least 3 ms before `COLOR_SEL`.
    - **Keys.** With no touch tail, Settings > Display > Frontlight sets brightness and warm/cool from the keys.
10. **B9 - Touch** (-T01C/-FT01C only; BRING_UP has no touch step, and §6 lists its currents). An I2C scan shows 0x38 (FT6336U) next to the RTC, and T11 shows its chip id (expect 0x64) accepted. This is a gate before release: a genuine tail the id check refuses (the reader logs `Device at 0x38 is not a FocalTech touch controller`) is never hibernated and draws about 165 µA more in every sleep. A GT911 tail (0x5D/0x14) needs the alternate jumpers and a build with `-DSILKSCREEN_TOUCH_ALT_JUMPERS=1`; on a default build it stays awake through every sleep (about 3.3 mA) and P2 reports `touch_not_probed`. Build with `-DTOUCH_PROBE_DEBUG` and log the probe (controller, address, cached result); a cold boot without the tail must boot touchless, with the keys, hints and remap. Map the corners and set `swapXY`/`flipX`/`flipY` and the raw ranges (the test firmware's T11 fits and logs them; T12 checks the sleep command). The keys still work with touch fitted. Sleep with the tail fitted:
    - `TP_RST` (`IO11`) is held HIGH (3.3 V), never LOW.
    - `IO41` is unheld for an FT6336U, and 0 V for a GT911.
    - The controller is hibernated: on a logic analyzer at sleep entry, the `0xA5 = 0x03` write is ACKed (or NACKed, then a reset and an ACK).
    - Current into `J4` pin 2 is about 55 µA (hibernate), against 220 µA in Monitor and ~1.1 mA with `TP_RST` LOW. Log it for a few minutes to catch a wake-up on the floating `IO41`.

    Unplug the tail while asleep and check that a cold boot finds it absent.
11. **B10 - Sleep current** (BRING_UP §6, and §4's back-feed probes). Follow [POWER.md §4](POWER.md#4-measurement-and-bench-checks) (MEAS-01) with a release build: a µA meter or logger in series with the cell at 3.8 V, USB and UART adapters off, card fitted, light off, panel asleep. Average 60 s, starting 60 s after sleep entry.
    - Expect ≈58-73 µA without touch and ≈113-130 µA with an FT6336U hibernated.
    - Measure with each panel. The GDEQ0426T82 sleeps at 2-6 µA. The UC8279D panel's figure is not in hand. Take it as the difference with the `J2` flex in and out, once the `R5` test below has ruled out back-feed, and record it in POWER.md (budget row 17).
    - Above ≈150 µA, work through the A/B list in POWER.md. It includes the J2-flex / R5 test for GPIO47/48 back-feed and the `espefuse` summary. In sleep the voltage across `R5` should be ≈0 V; every 0.1 V is 10 µA into `IO47` (§6.1). Across `R34` (33 Ω in `BUSY`) it should be ≈0 mV; every 1 mV is 30 µA into `IO48`.

### Notes for steps 6 and 7 (pinned core: Arduino-ESP32 3.3.11)

- **Front light (as built).** LEDC stays attached while awake; the pad moves between the plain GPIO output register (dark, and the enable pulse) and the LEDC signal through the GPIO matrix (`gpio_set_direction`, then `ledcOutputInvert(pin, false)`, which also clears the stale `GPIO_OUT` bit so a later detach or `pinMode` lands LOW). None of these touch a pull. `ledcDetach()` (sleep handover only) routes the pad back to `GPIO_OUT` and frees the channel and timer: no pin reset, no pull change. Arduino 3.x clocks LEDC from the 40 MHz XTAL, so 25 kHz allows 10 bits (1600 ≥ 1024), not 11; a `static_assert` in the profile checks it. The monitor runs on the esp_timer task (8 KB stack) and skips a tick rather than block while a light transition holds the front-light lock.
- **Touch (as built).** The touch `begin` paths run from `gpio.begin()`, before `halClock.begin()`, and Wire ignores a second master `begin`, so the first driver to start the bus sets its clock. Every touch path and every sensor driver now starts the bus through `freeink::i2c::beginBus()` at `busHz()`: the sensor-bus clock when the pins match, otherwise the path's old rate. Every existing board with touch on its sensor bus (X4 Pro, LilyGo, PaperS3, EEGO A4, Paper Mono) already had equal clocks, so none changes. The stuck-bus check runs only on the first start of an `i2cBusRecovery` bus and never under a running controller (Arduino's pin manager is checked first). The probe result sits in `RTC_DATA_ATTR` with a magic word and is trusted only when the reset reason is a deep-sleep wake. `HalPowerManager::startDeepSleep()` runs `gpio.prepareForSleep()` and `releaseSensorBusForSleep()` first, before the serial teardown, so every sleep path gets them and their logs reach the host. A present FT6336U adds the reset and settle time (~307 ms) to each boot, and to a sleep entry whose hibernate write is NACKed. With `earlyWakeDecision` the probe runs after the wake decision (`gpio.begin(true)`, then `gpio.startTouch()`), so it no longer lengthens the hold a wake needs or a ghost wake's awake time. A sleep entry before the probe sends an FT6336U nothing after a deep-sleep wake (it is as the last sleep entry left it) and one best-effort hibernate write after any other reset; a GT911 cached by the probe gets its sleep command or its `INT` hold again. The abnormal-reset sleep resets an FT6336U and sends hibernate once.
